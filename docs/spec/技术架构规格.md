### v0.2 变更说明（相对 v0.1）

- **认证改为自建**：平台后端签发 / 校验 JWT，不再使用 CloudBase 身份认证（其黑盒与自定义登录问题见 `test/M4-数据库验证结论.md`）。
- **数据库改为自建 PostgreSQL（VPS/CVM）**：每游戏独立**数据库** + 专属 role + 连接串，**沙盒与托管均 PG 协议直连**（CloudBase PG 不支持建 role、沙盒也无法直连）。
- **CloudBase 角色收敛**：仅**云托管（CloudRun）用于发布出去的游戏服务**；平台后端 / Agent / **平台前端**均部署在**自建 VPS**；对象存储使用**腾讯云 COS 独立桶**（与 AGS StorageMount 同一个桶，**非** CloudBase 托管桶）；**不再承担身份、数据库、平台前端与平台自身托管**。
- **数据模型精简**：`users`（无 `role`）、**无会话表**（认证为**无状态 JWT**）、**无数据库开通记录表**（开通是游戏创建的幂等副作用）。
- 相应更新：数据模型（新增 `users`）、开发态数据库开通、发布态注入 `DATABASE_URL`、认证章节、里程碑与开放问题。

### v0.2.1 变更说明（2026-10-08，实测后）

- **隔离单位改为「每游戏独立数据库」**：游戏库 `game_{sid}` + 专属 role `game_{sid}_rw`；平台元数据独立库 `aigame_platform`。开通**必须** `REVOKE CONNECT ON DATABASE … FROM PUBLIC`（PostgreSQL 默认 PUBLIC 可连所有库，实测不收回会**越库**）。
- **发布 API 链路已实测**：后端不需 MCP/控制台，直接调云托管 OpenAPI（`tcb:DescribeCloudBaseBuildService` → 上传源码包 → `tcbr:CreateCloudRunServer` / `UpdateCloudRunServer`）；见 `test/M6b-API部署与连库验证结论.md`。
- **沙盒 → 自建 PG 公网直连已实测**：TCP 可达、建表/写入成功、往返 <1s，无需 VPC/VPN。
- **SSL 暂不启用（已知风险）**：当前 VPS PG `ssl=off`，连接为明文；DSN 暂用 `sslmode=disable`，**上线前必须启用 SSL 并改为 `require`**（见 Q1/Q8）。
- CloudBase 角色收敛为**仅云托管（CloudRun）**；平台前端由 **VPS Nginx** 托管。

## 1. 概述

### 1.1 产品目标

面向无编程基础的用户：用自然语言与 AI 多轮对话，生成一个**带服务端的可玩游戏**，在平台内实时预览与调试，并**一键发布到公网**，通过链接分享给他人游玩。

### 1.2 最小技术闭环（本期目标）

1. 用户注册/登录，创建/进入一个游戏。
2. 用户与 AI 多轮对话，AI 在云端沙盒中编写并运行该游戏的代码。
3. 平台前端实时展示沙盒内浏览器的画面，用户可直接操作，同时能看到 AI 的操作。
4. 游戏若需要持久化，使用平台分配的独占数据库（每游戏独立 database + role）。
5. AI 调用发布工具，把该游戏的前端与后端部署到云端，返回公网可玩链接。

### 1.3 范围外（本期不做）

- 游戏大厅、社交分享、评论。
- AI 生成图片/音频素材。
- 视觉模型自动试玩与自动修复闭环。
- 灰度发布、A/B、多区域、CDN 优化。
- 复杂多人在线匹配系统（游戏自身可自行实现，但平台不提供统一房间服务）。
- 第三方社交登录（微信 / Apple / Google 等，后续按需接入）。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 用户 | 在平台注册并登录的创作者；平台自有账号体系。 |
| 游戏（Game） | 一个逻辑作品，拥有唯一代码工作区、数据库与版本历史。 |
| 会话（Thread） | 针对某个游戏的一次多轮对话；一个游戏可有多个会话。 |
| 版本（Version） | 一次发布产生的不可变代码快照与部署记录。 |
| 工作区（Workspace） | 游戏源码所在目录，位于沙盒 `/workspace/work`，直接挂载到对象存储 `games/{game_id}/`，读写实时持久化。 |
| 沙盒（Sandbox） | 云端的隔离开发环境，承载游戏服务、浏览器与 Agent 操作入口。 |
| 预览（Preview） | 沙盒内浏览器的实时画面，映射到平台前端右栏。 |
| 发布（Publish） | 将工作区部署为一个公网可访问的游戏服务。 |

### 3.2 部署与地域

- 平台后端（api）、Agent 运行时、**平台前端（Nginx 静态托管）** 均部署在**自建 VPS**，与自建 PostgreSQL 同机或同内网：低延迟，且平台自身访问数据库**无需**走公网。
- 开发沙盒（AGS）与发布出去的游戏服务（CloudRun）部署在**腾讯云 / CloudBase（上海）**。
- **自建 PostgreSQL 应当选择与上海相近的节点**，开启公网访问（**SSL 暂未启用，见 Q1/Q8**）；沙盒（开发态）与游戏服务（发布态）经公网访问。
- 发布出去的游戏服务运行在**云托管（CloudRun）**，通过注入的 `DATABASE_URL` 访问自建 PG。

### 3.3 组件职责与信任边界

| 组件 | 职责 | 持有凭证 |
|---|---|---|
| 产品前端 | 登录、对话、版本展示、预览画面 | 平台 access_token（自签 JWT） |
| 平台后端 api | 认证（签发/校验）、沙盒编排、预览反代、数据库开通、发布、鉴权 | 全部云端凭证（AGS API Key、CloudBase 服务端凭证、**自建 PG 管理员凭证**） |
| Agent 运行时 | 对话编排、工具调用 | 仅沙盒访问权（E2B API Key）+ 平台内部接口令牌 + 平台 JWT 公钥（验签） |
| 云沙盒 | 运行游戏服务、浏览器、Agent 文件操作 | 无云端管理凭证；仅持**本游戏 `DATABASE_URL`**（经环境变量注入） |
| CloudBase | 托管（CloudRun，仅游戏服务） | 平台侧服务端凭证 |
| 腾讯云 COS（独立桶） | 工作区 / 素材 / 版本包（与 AGS 挂载同一桶） | 平台侧 COS 访问凭证（CAM） |
| 自建 PostgreSQL | 平台元数据库（`aigame_platform`）+ 每游戏独立数据库 | 管理员凭证**仅**平台后端持有；游戏服务仅持自身 DSN |

**强制要求**：

- R-SEC-1：Agent **禁止**持有任何云端管理凭证；需要管理权限的动作（开通数据库、发布、部署）**必须**经由平台后端执行。
- R-SEC-2：游戏代码**禁止**接触任何平台凭证；它只读取平台注入的环境变量。

## 5. 领域模型与数据模型

### 5.1 实体关系

```
用户 1 ── N 游戏
游戏 1 ── N 会话
游戏 1 ── N 版本
游戏 1 ── 1 数据库（+ 专属 role）
游戏 1 ── 1 托管服务
```

**核心约束（必须）**：

- R-DOM-1：**工作区、沙盒、数据库均以「游戏」为隔离单位，不以「会话」为单位。**
- R-DOM-2：同一游戏的多个会话编辑**同一份工作区代码**。
- R-DOM-3：游戏归属于唯一用户（`games.owner_id → users.user_id`）。
- R-DOM-4：数据库开通是**游戏创建的幂等副作用**（database / role 存在则跳过，**不重建、不改密码**），**不设**独立开通记录表；在线版本由版本表派生，**不得**增设冗余列。

### 5.2 数据表（平台元数据：`aigame_platform` 库的 `platform` schema）

```
users
  user_id       uuid PK
  username      varchar(64) unique     -- 登录名（用户名或邮箱）
  password_hash text                   -- argon2id
  status        varchar(16)            -- active | disabled
  created_at, updated_at

games
  game_id       uuid PK
  owner_id      uuid → users
  name          text
  status        text                   -- active | archived
  sandbox_id    text null              -- AGS 沙盒实例 ID（外部分配、不可推导；用于复用）
  public_url    text null              -- 公网链接（平台分配，不可推导，跨版本稳定）
  created_at, updated_at

game_threads
  thread_id     uuid PK                -- Agent 会话 ID
  game_id       uuid → games
  title         text
  status        text                   -- active | archived
  created_at, updated_at

game_versions
  version_id       uuid PK
  game_id          uuid → games
  seq              int                 -- 每游戏递增
  source_thread_id uuid → game_threads
  note             text
  status           text                -- building | deploying | deployed | failed
  revision         text null           -- 部署产生的托管版本标识（外部平台分配）
  created_at, deployed_at
```

**字段设计原则（必须）**：

- **不落地可推导的状态**：**当前在线版本**由「该游戏 `status='deployed'` 且 `seq` 最大的版本」派生，**不设** `current_version_id`；`game_versions.status` 只表达发布流水。
- **1:1 关系不拆表**：版本的发布结果（`revision` / `status` / `deployed_at`）**内联在 `game_versions`**。
- **只保留两类字段**：**归属键**与**外部系统产物标识**（如 `sandbox_id`、`public_url`、`revision`）；平台自定名（托管服务名 `game-{game_id}`、库/role 名）按约定派生，**不落列**。
- **稳定值归属游戏**：一游戏一托管服务，`public_url` 属于 `games`。
- **连接串不落库**：主机/端口来自平台配置；库名由 `sid` 派生、role 密码由 `HMAC(master_secret, game_id)` 派生（见 §5.3），故不存每游戏连接凭据，也**不设**数据库开通记录表。
- **口令哈希存储**：`password_hash` 用 argon2id。

### 5.3 资源命名与路径映射（契约）

**归属链**：

```
user_id ──(games.owner_id)──▶ game_id ──▶ 沙盒 / 对象存储 / 数据库 / 托管服务
```

- `user_id`：平台生成的 UUID，一个用户拥有多个游戏。
- `game_id`：平台生成的 UUID，全局唯一，是**所有外部资源的命名根**。

**统一命名根**：

```
sid = replace(game_id, '-', '')     -- 32 位十六进制，路径与标识符安全
```

**映射表**：

| 资源 | 命名 / 路径 | 派生自 |
|---|---|---|
| 沙盒标识 | `metadata.game_id = {game_id}`；实例 ID 落 `games.sandbox_id` | game_id |
| 沙盒工作区（可写） | 沙盒 `/workspace/work` ⇄ COS `games/{game_id}/**`（存储挂载） | 固定 + game_id |
| 沙盒素材（只读） | 沙盒 `/workspace/input` ⇄ COS `games/{game_id}/input/**` | 固定 + game_id |
| 存储挂载（Tool 级） | `StorageMount{Name:"work", BucketPath:"/games", MountPath:"/workspace/work"}`，**不传 Endpoint** | 固定 |
| 存储挂载（Instance 级） | `metadata["x-mounts"]`：`subPath={game_id}` → `/workspace/work`；`subPath={game_id}/input` → `/workspace/input`（只读） | game_id |
| 对象存储·版本包 | `games/{game_id}/versions/{seq}.tar` | game_id + seq |
| 游戏数据库 | `game_{sid}` | game_id |
| 数据库 role | `game_{sid}_rw` | game_id |
| 数据库密码 | `base64url(HMAC-SHA256(master_secret, game_id))` | game_id + 平台主密钥 |
| 数据库连接串 | `postgresql://game_{sid}_rw:<pwd>@<PG_HOST>:<PG_PORT>/game_{sid}?sslmode=disable`（SSL 启用后改 `require`） | 派生，**不落库** |
| 托管服务名 | `game-{game_id}` | game_id |
| 公网链接 | 平台分配，落 `games.public_url` | 部署返回值（不可推导） |

**约束（必须）**：

- R-MAP-1：沙盒、对象存储、数据库、托管服务的命名**必须**仅由 `game_id` 推导。
- R-MAP-2：同一游戏的源码、素材、版本包**必须**落在 `games/{game_id}` 前缀下。
- R-MAP-3：`user_id` **不得**出现在路径或外部资源名中，只存在于 `games.owner_id`。
- R-MAP-4：游戏数据库连接串**必须**按约定派生（库名 / role / 密码 / 主机），**不得**落库为明文。

## 6. 开发态流程

### 6.1 创建与进入

1. 用户登录后，前端请求「我的游戏」列表。
2. 新建游戏：平台创建 `games` 记录与第一个 `game_threads`，并开通该游戏的数据库（§6.5）。
3. 继续游戏：在已有游戏下创建新的 `game_threads`，复用同一工作区与数据库。

### 6.2 沙盒生命周期与存储

**存储模型（必须）**：使用 **AGS 原生 COS 存储挂载**。沙盒内 `/workspace/work` 直接就是 COS 目录，读写**实时落到对象存储**；无需自研同步、无需自研快照。

**配置分层**：

| 层 | 配置 | 说明 |
|---|---|---|
| Tool 级 | 一个 COS `StorageMount`：`BucketPath=/games` → `MountPath=/workspace/work` | 所有游戏共用；**不得传 `Endpoint`** |
| Instance 级 | `metadata["x-mounts"]`（标准 E2B 扩展） | 用 `subPath={game_id}` 实现每游戏隔离 |

```python
sandbox = Sandbox.create(
    template="ai-game-platform-…",       # Tool 名（挂载定义在其上）
    timeout=3600,
    metadata={
        "game_id": game_id,
        "x-mounts": json.dumps([
            {"name": "work", "subPath": game_id,            "mountPath": "/workspace/work"},
            {"name": "work", "subPath": f"{game_id}/input", "mountPath": "/workspace/input", "readOnly": True},
        ]),
    },
)
# 访问挂载点必须以 root 执行
sandbox.commands.run("ls /workspace/work", user="root")
```

**实测事实**：

- 沙盒写 `/workspace/work/x` → COS `games/{game_id}/x` **立即出现**；
- 往 COS 放对象 → 沙盒 `/workspace/work` **立即可见可读**；
- 销毁并用同一 `subPath` 重建 → 数据**仍在**（真持久化）；
- 挂载呈现为 `virtiofs`；`node_modules` 等依赖**必须**烘入沙盒镜像、**不得**放挂载层。

**约束（必须）**：

- R-SBX-1：工作区持久化**只**依赖 COS 挂载；`node_modules` 等可再生成依赖**必须**烘入镜像。
- R-SBX-2：Tool 级挂载**不得**设置 `Endpoint`，由 AGS 按地域自动补全。
- R-SBX-3：每次挂载前，COS 中的 `SubPath` 目录**必须**已存在。
- R-SBX-4：沙盒内访问挂载点**必须**以 `user="root"` 执行命令。
- R-SBX-5：`pause/resume` 仅为**可选**加速手段；如使用须 `keep_memory=False`。

**生命周期**：

```
ensure(game_id)
  → 确保 COS 前缀 games/{game_id}/ 存在
  → 以 metadata.game_id + x-mounts(subPath=game_id) 创建/复用沙盒（ID 存 games.sandbox_id）
  → 注入本游戏 DATABASE_URL
  → 确保游戏服务进程运行
```

### 6.3 预览（NoVNC 同源反代）

- 沙盒内置浏览器（Chromium）与 NoVNC 服务；Agent 通过 CDP 操作浏览器。
- 平台前端以**同源 iframe** 嵌入预览；由平台后端反代 NoVNC 与 WebSocket。
- 要求：
  - R-PRE-1：NoVNC 的访问令牌**不得**暴露给浏览器；由后端持有并注入。
  - R-PRE-2：反代**必须**同时支持 HTTP 与 WebSocket。
  - R-PRE-3：预览地址**必须**带 `resize=scale`，并提供「适应窗口 / 原始比例」切换。

### 6.4 Agent 与工具

Agent 基于 deepagents 构建，运行在 LangGraph Server 上。除框架内置的终端与文件工具外，**必须**提供以下自定义工具：

| 工具 | 作用 |
|---|---|
| `provision_database()` | 为当前游戏开通独占数据库（database + role），返回连接串并写入工程环境变量 |
| `restart_server()` | 重启游戏服务进程，返回启动日志 |
| `screenshot()` | 对沙盒浏览器截图，供自检（限次） |
| `publish_game(name)` | 校验并发布当前游戏，返回公网链接 |

**约束**：

- R-AGT-1：Agent 只改生成区代码，不得修改平台模板与构建脚本。
- R-AGT-2：Agent 必须保证 `npm run dev` 能启动游戏服务。
- R-AGT-3：为控制单轮时长，自检轮数**必须**设上限，成型即发布。
- R-AGT-4：Agent 不得调用任何云管理 API，只能调用平台内部接口。

### 6.5 数据库开通

平台后端以**自建 PostgreSQL 管理员**身份连接并执行（管理员凭证**仅**平台后端持有，绝不下发沙盒）。**开通是幂等副作用**：不存在则创建，存在则跳过；**不重建库、不改密码**（避免滚动更新期间旧实例凭据失效）。

```sql
-- 一次性：平台元数据库
CREATE DATABASE aigame_platform;
REVOKE CONNECT ON DATABASE aigame_platform FROM PUBLIC;
CREATE ROLE platform_rw LOGIN PASSWORD '<platform_pwd>';
GRANT CONNECT ON DATABASE aigame_platform TO platform_rw;
-- （连入 aigame_platform 后按 §5.2 建表并授权）

-- 每游戏（幂等）
CREATE DATABASE game_{sid};
REVOKE CONNECT ON DATABASE game_{sid} FROM PUBLIC;      -- 关键：否则任意 role 都能连任意库
CREATE ROLE game_{sid}_rw LOGIN PASSWORD '<pwd>';       -- pwd = HMAC(master_secret, game_id)
GRANT CONNECT ON DATABASE game_{sid} TO game_{sid}_rw;
-- （连入 game_{sid} 库）
GRANT USAGE, CREATE ON SCHEMA public TO game_{sid}_rw;
```

返回连接串（派生，不落库）：

```
postgresql://game_{sid}_rw:<pwd>@<PG_HOST>:<PG_PORT>/game_{sid}?sslmode=disable
（SSL 启用后必须改为 sslmode=require）
```

**要求**：

- R-DB-1：每个游戏**必须**拥有独立**数据库**与独立 role，且 role **仅能连接该库**（连其它游戏库必须被拒绝）。
- R-DB-2：游戏服务**必须**通过 PostgreSQL 协议直连数据库。
- R-DB-3：连接串**必须**由平台按 §5.3 派生；Agent 不得持有管理员凭证。
- R-DB-4：开通**必须**执行 `REVOKE CONNECT ON DATABASE … FROM PUBLIC`（PostgreSQL 默认 PUBLIC 可连所有库，实测不收回会**越库**）。
- R-DB-5：数据库对公网暴露时**必须**启用 SSL（`sslmode=require`）与 role 最小权限；**当前 VPS PG 尚未启用 SSL（已知风险，见 Q1/Q8），启用前暂用 `sslmode=disable`**。
- R-DB-6：**管理员凭证仅平台后端持有**；游戏服务只读平台注入的 `DATABASE_URL`。
- R-DB-7：平台元数据库（`aigame_platform`）与游戏库**同实例隔离**；游戏 role **不得**连接平台元数据库（两库均需收 PUBLIC CONNECT）。

## 7. 发布态流程

### 7.1 发布

```
publish_game(name)                    # 由当前会话发起
 → 由 thread_id 解析 game_id
 → 运行构建与校验（见 7.4）
 → 打包工作区 → 对象存储 games/{game_id}/versions/{seq}.tar
 → 部署/更新托管服务 game-{game_id}
     · 调云托管 OpenAPI：tcb:DescribeCloudBaseBuildService → PUT 上传源码包
       → tcbr:CreateCloudRunServer / UpdateCloudRunServer（Items：AccessTypes=PUBLIC、Port、EnvParam=…）
     · 注入环境变量：DATABASE_URL / PORT / NODE_ENV
     · 开启公网访问；配置健康检查
     · 部署进行中再次提交会 ResourceInUse → 必须轮询/重试
 → 写入 game_versions（seq+1，含 revision 与发布状态），更新 games.public_url（若首次）
 → 返回该版本公网链接
```

### 7.2 运行形态（必须：单服务同源）

- 一个游戏 = 一个托管服务，**同一服务**同时提供：静态前端、HTTP API、WebSocket。
- 游戏代码内部一律使用**相对路径**访问自身接口，保证同源、零配置。
- 单一公网链接对外。
- WebSocket 受云托管 **60s 空闲断开**约束，**必须**实现心跳（建议每 10s）。

### 7.3 版本

- 版本**只增不改**：每次发布产生一个不可变版本（seq+1），并生成托管平台的新 revision；发布结果内联在版本记录中。
- **当前在线版本** = 该游戏 `status='deployed'` 且 `seq` 最大的版本（派生，不落列）。
- `public_url` 跨版本稳定，属于游戏。
- 本期**不提供回滚**；历史版本产物保留留档。

### 7.4 发布前校验（必须）

- 产物存在且可构建成功。
- 服务监听约定端口，`/api/health` 返回正常。
- 源码中不得出现绝对域名、绝对端口、外部服务地址。
- 若使用数据库，**必须**经注入的 `DATABASE_URL` 访问，不得硬编码。

## 8. 认证与授权（自建）

### 8.1 认证

- 平台后端提供注册 / 登录 / 刷新接口，账号体系为平台自有（`users` 表）。
- 登录成功签发 **无状态 JWT**（不做服务端会话存储）：
  - **access_token**：JWT，**RS256** 签名，有效期建议 2 小时；claims：`iss` / `aud` / `sub`（`user_id`）/ `exp` / `iat` / `jti`。
  - **refresh_token**：同为自包含 JWT（`typ=refresh`），有效期建议 30 天；`/auth/refresh` 校验其签名与类型后换发新 access_token。
- 平台后端发布 **JWKS**（`/.well-known/jwks.json`）。
- 请求携带 `Authorization: Bearer <access_token>`。
- **平台后端与 Agent 运行时必须各自本地验签**（通过 JWKS 公钥，带缓存与按 `kid` 刷新）：

```
校验顺序：
  1) 取 JWKS 公钥（缓存，kid 刷新）
  2) 验签（RS256）
  3) 校验 iss / aud / exp
  4) 取 sub 作为 user_id
```

- R-AUTH-1：日常请求**不得**因验签而调用外部服务（公钥本地缓存即可）。
- R-AUTH-2：Agent 运行时**独立**验签，不得引入「由一方代验」的中转接口。
- R-AUTH-3：令牌**无服务端状态**；登出为客户端丢弃，`exp` 前无法撤销（如需强制吊销，后续引入令牌黑名单或会话版本号）。

### 8.2 授权（平台侧）

- 认证解决「你是谁」，授权解决「你能做什么」，授权**必须**由平台后端实现。
- 归属校验：游戏归属 `games.owner_id`；会话经 `game_threads` 归属到游戏。
- 所有对游戏/版本/会话的操作**必须**校验其属于当前用户。

### 8.3 与游戏数据库的关系

- 游戏数据库使用独占数据库 + 专属 role，**与平台账号体系解耦**：用户的登录凭证 ≠ 游戏数据库凭证。
- 游戏服务仅持本游戏 `DATABASE_URL`；平台管理员凭证不下发。

## 9. 接口契约

### 9.1 认证（公开）
