## 1. 概述

### 1.1 产品目标

面向无编程基础的用户：用自然语言与 AI 多轮对话，生成一个**带服务端的可玩游戏**，在平台内实时预览与调试，并**一键发布到公网**，通过链接分享给他人游玩。

### 1.2 最小技术闭环（本期目标）

1. 用户登录，创建/进入一个游戏。
2. 用户与 AI 多轮对话，AI 在云端沙盒中编写并运行该游戏的代码。
3. 平台前端实时展示沙盒内浏览器的画面，用户可直接操作，同时能看到 AI 的操作。
4. 游戏若需要持久化，使用平台分配的独占数据库。
5. AI 调用发布工具，把该游戏的前端与后端部署到云端，返回公网可玩链接。

### 1.3 范围外（本期不做）

- 游戏大厅、社交分享、评论。
- AI 生成图片/音频素材。
- 视觉模型自动试玩与自动修复闭环。
- 灰度发布、A/B、多区域、CDN 优化。
- 复杂多人在线匹配系统（游戏自身可自行实现，但平台不提供统一房间服务）。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 用户 | 通过 CloudBase 身份认证登录的创作者。 |
| 游戏（Game） | 一个逻辑作品，拥有唯一代码工作区、数据库与版本历史。 |
| 会话（Thread） | 针对某个游戏的一次多轮对话；一个游戏可有多个会话。 |
| 版本（Version） | 一次发布产生的不可变代码快照与部署记录。 |
| 工作区（Workspace） | 游戏源码所在目录，位于沙盒 `/workspace/work`，持久化在对象存储。 |
| 沙盒（Sandbox） | 云端的隔离开发环境，承载游戏服务、浏览器与 Agent 操作入口。 |
| 预览（Preview） | 沙盒内浏览器的实时画面，映射到平台前端右栏。 |
| 发布（Publish） | 将工作区部署为一个公网可访问的游戏服务。 |

### 3.2 部署与地域

- 全部资源部署在**同一地域（上海）**，以保证沙盒、数据库、托管之间网络可达与低延迟。
- 平台后端与 Agent 运行时以**云托管（CloudRun）服务**形式部署。
- 云沙盒使用与云托管同地域的实例。

### 3.3 组件职责与信任边界

| 组件 | 职责 | 持有凭证 |
|---|---|---|
| 产品前端 | 登录、对话、版本展示、预览画面 | CloudBase Publishable Key + 用户 access_token |
| 平台后端 api | 沙盒编排、预览反代、数据库开通、发布、鉴权 | 全部云端凭证（AGS API Key、CloudBase 服务端 API Key、PG 管理凭证） |
| Agent 运行时 | 对话编排、工具调用 | 仅沙盒访问权（E2B API Key）+ 平台内部接口令牌 |
| 云沙盒 | 运行游戏服务、浏览器、Agent 文件操作 | 无云端管理凭证 |
| CloudBase | 身份、数据、对象存储、托管 | 平台侧服务端凭证 |

**强制要求**：

- R-SEC-1：Agent **禁止**持有任何云端管理凭证，所有需要管理权限的动作（开通数据库、发布、部署）**必须**经由平台后端执行。
- R-SEC-2：游戏代码**禁止**接触任何平台凭证；它只读取平台注入的环境变量。

## 5. 领域模型与数据模型

### 5.1 实体关系

```
用户 1 ── N 游戏
游戏 1 ── N 会话
游戏 1 ── N 版本
游戏 1 ── 1 数据库 schema
游戏 1 ── 1 托管服务
```

> 「用户」是外部身份，由身份认证服务维护；平台侧仅以 UID 引用，不建本地用户表。

**核心约束（必须）**：

- R-DOM-1：**工作区、沙盒、数据库 schema 均以「游戏」为隔离单位，不以「会话」为单位。**
- R-DOM-2：同一游戏的多个会话编辑**同一份工作区代码**。
- R-DOM-3：游戏归属于唯一用户（`owner_id`，值为身份认证 UID；**用户身份不落平台表**）。
- R-DOM-4：数据库信息以 `game_databases` 为唯一来源；在线版本由版本表派生，**不得**增设冗余列或在其它表冗余同一事实。

### 5.2 数据表（平台 schema）

```
games
  game_id            uuid PK
  owner_id           varchar(64)       -- 身份服务 UID（JWT sub，外部不透明字符串；与身份库 auth.users.id 同为 varchar(64)）
  name               text
  status             text              -- active | archived
  public_url         text null         -- 公网链接（平台分配，不可推导，跨版本稳定）
  created_at, updated_at

game_threads
  thread_id     uuid PK                -- Agent 会话 ID
  game_id       uuid → games
  title         text
  status        text                   -- active | archived
  created_at, updated_at

game_versions
  version_id       uuid PK
  game_id          uuid → games
  seq              int                 -- 每游戏递增
  source_thread_id uuid → game_threads
  note             text
  status           text                -- building | deploying | deployed | failed
  revision         text null           -- 部署产生的托管版本标识（外部平台分配）
  created_at, deployed_at

game_databases
  game_id     uuid PK → games
  secret_ref  text                     -- 指向密钥管理中的连接凭据（外部系统引用）
  created_at
```

**字段设计原则（必须）**：

- **不落地外部系统已提供的身份/资料数据**：用户身份与资料由身份认证服务提供，平台只引用 UID，**不建用户镜像表**（避免首登同步、双写漂移）。
- **不落地可由已有字段推导出的状态**：**当前在线版本**由「该游戏 `status='deployed'` 且 `seq` 最大的版本」派生，**不设** `current_version_id` 冗余列；`game_versions.status` 只表达该版本的发布流水（`building | deploying | deployed | failed`），**不得**再表达"当前在线/已被取代"。
- **1:1 关系不拆表**：一个版本仅发布一次，其发布结果（`revision` / `status` / `deployed_at`）**内联在 `game_versions`**，不另设部署表。
- **只保留两类字段**：**归属键**（`game_id` / `version_id` / `thread_id`）与**外部系统产物标识**。后者仅收纳**外部平台分配、不可推导**的值（如 `public_url`、`revision`）；平台自定名（如托管服务名 `game-{game_id}`、数据库 `schema`/`role` 名）按约定派生，**不落列**。
- **稳定值归属游戏**：一游戏一托管服务，`public_url` 是**服务级**事实（跨版本稳定），属于 `games`；放到版本会重复同一值。仅当未来出现「每版本独立地址」（灰度/预览）时才下沉。
- **数据库信息唯一来源**：以 `game_databases` 为唯一来源；判断某游戏是否已开通数据库，以该表是否存在对应行（`game_id` 为主键，1:1）为准。

### 5.3 资源命名与路径映射（契约）

**归属链**：

```
user_id ──(games.owner_id)──▶ game_id ──▶ 沙盒 / 对象存储 / 数据库 / 托管服务
```

- `user_id`：身份服务 UID；一个用户拥有多个游戏，`games.owner_id = user_id`。列某用户的游戏即 `SELECT game_id FROM games WHERE owner_id = ?`。
- `game_id`：平台生成的 UUID，全局唯一，是**所有外部资源的命名根**。
- `user_id` **不作为路径段或资源名**：它是外部不透明字符串（长度 ≤64、字符集不保证、可能含 `/`），进路径不安全；归属只经 `games.owner_id` 关联。

**统一命名根**：

```
sid = replace(game_id, '-', '')     -- 32 位十六进制，路径与标识符安全
```

**映射表**：

| 资源 | 命名 / 路径 | 派生自 |
|---|---|---|
| 沙盒实例名 | `game-{game_id}` | game_id |
| 沙盒工作区（可写） | `/workspace/work` | 固定 |
| 沙盒素材（只读） | `/workspace/input` | 固定 |
| 对象存储·工作区 | `games/{game_id}/work/**` | game_id |
| 对象存储·素材 | `games/{game_id}/input/**` | game_id |
| 对象存储·版本包 | `games/{game_id}/versions/{seq}.tar` | game_id + seq |
| 工作区挂载配置 | Tool `BucketPath=/games`；Instance `SubPath={game_id}`、`MountPath=/workspace/work` | game_id |
| 素材挂载配置 | 同源；Instance `SubPath={game_id}/input`、`MountPath=/workspace/input`、`ReadOnly=true` | game_id |
| 数据库 schema | `game_{sid}` | game_id |
| 数据库 role | `game_{sid}_rw` | game_id |
| 托管服务名 | `game-{game_id}` | game_id |
| 公网链接 | 平台分配，落 `games.public_url` | 部署返回值（不可推导） |

**会话与版本**：`game_threads.game_id`、`game_versions.game_id` 均指向游戏；同一游戏的多个会话共享同一工作区；版本包路径中的 `{seq}` 取自 `game_versions.seq`。

**约束（必须）**：

- R-MAP-1：沙盒、对象存储、数据库、托管服务的命名**必须**仅由 `game_id` 推导，不得引入其它可变因素。
- R-MAP-2：同一游戏的源码、素材、版本包**必须**落在 `games/{game_id}` 前缀下，保证按游戏隔离与整体清理。
- R-MAP-3：`user_id` **不得**出现在路径或外部资源名中，只存在于平台元数据 `games.owner_id`。

## 6. 开发态流程

### 6.1 创建与进入

1. 用户登录后，前端请求「我的游戏」列表。
2. 新建游戏：平台创建 `games` 记录与第一个 `game_threads`。
3. 继续游戏：在已有游戏下创建新的 `game_threads`，复用同一工作区。

### 6.2 沙盒生命周期与存储

**存储模型（必须）**：使用 AGS 原生存储挂载，不实现自研快照。

- 沙盒工具（Tool）级定义对象存储来源与默认挂载点。
- 实例（Instance）级通过 `SubPath = {game_id}` 实现每游戏隔离。

```jsonc
// Tool 级
"StorageMounts": [{
  "Name": "cos-games",
  "StorageSource": { "Cos": { "BucketName": "<bucket>", "BucketPath": "/games" } },
  "MountPath": "/workspace/work",
  "ReadOnly": false
}]

// Instance 级
"MountOptions": [{
  "Name": "cos-games",
  "SubPath": "<game_id>",
  "MountPath": "/workspace/work"
}]
```

字段含义：

- `BucketName`：目标对象存储桶。
- `BucketPath`：**桶内的基准目录**，工具级、所有游戏共用（此处 `/games`）。
- `SubPath`：在基准目录下再切一层的**实例级子目录**，实现每游戏隔离（此处 `{game_id}`）。
- `MountPath`：该存储内容在**沙盒内**出现的目录（此处 `/workspace/work`）。

因此：沙盒内 `/workspace/work/main.js` ⇄ 对象存储对象 `games/{game_id}/main.js`；挂载点之外的目录（如 `/opt/deps`、`/tmp`）仍是临时的。

- 效果：`对象存储 games/{game_id}` ⇄ 沙盒 `/workspace/work`；实例销毁后以相同 `SubPath` 重建即可恢复源码。
- 依赖（`node_modules`）**必须**烘入沙盒镜像，**不得**放在挂载层。
- 沙盒可配置空闲超时自动销毁，无需销毁回调。

**生命周期**：

```
ensure(game_id)
  → 按 game-{game_id} 查找沙盒
  → 不存在则创建（挂载 SubPath=game_id）
  → 确保游戏服务进程运行
```

### 6.3 预览（NoVNC 同源反代）

- 沙盒内置浏览器（Chromium）与 NoVNC 服务；Agent 通过 CDP 操作浏览器。
- 平台前端以**同源 iframe** 嵌入预览；由平台后端反代 NoVNC 与 WebSocket。
- 要求：
  - R-PRE-1：NoVNC 的访问令牌**不得**暴露给浏览器；由后端持有并注入。
  - R-PRE-2：反代**必须**同时支持 HTTP 与 WebSocket。

### 6.4 Agent 与工具

Agent 基于 deepagents 构建，运行在 LangGraph Server 上。除框架内置的终端与文件工具外，**必须**提供以下自定义工具：

| 工具 | 作用 |
|---|---|
| `provision_database()` | 为当前游戏开通独占数据库（schema + role），返回连接串并写入工程环境变量 |
| `restart_server()` | 重启游戏服务进程，返回启动日志 |
| `screenshot()` | 对沙盒浏览器截图，供自检（限次） |
| `publish_game(name)` | 校验并发布当前游戏，返回公网链接 |

**约束**：

- R-AGT-1：Agent 只改生成区代码，不得修改平台模板与构建脚本。
- R-AGT-2：Agent 必须保证 `npm run dev` 能启动游戏服务。
- R-AGT-3：为控制单轮时长，自检轮数**必须**设上限，成型即发布。
- R-AGT-4：Agent 不得调用任何云管理 API，只能调用平台内部接口。

### 6.5 数据库开通

平台后端以管理员身份执行：

```sql
CREATE SCHEMA IF NOT EXISTS game_{sid};
CREATE ROLE game_{sid}_rw LOGIN PASSWORD '<random>';
GRANT USAGE, CREATE ON SCHEMA game_{sid} TO game_{sid}_rw;
GRANT ALL ON ALL TABLES    IN SCHEMA game_{sid} TO game_{sid}_rw;
GRANT ALL ON ALL SEQUENCES IN SCHEMA game_{sid} TO game_{sid}_rw;
ALTER DEFAULT PRIVILEGES IN SCHEMA game_{sid} GRANT ALL ON TABLES    TO game_{sid}_rw;
ALTER DEFAULT PRIVILEGES IN SCHEMA game_{sid} GRANT ALL ON SEQUENCES TO game_{sid}_rw;
REVOKE ALL ON SCHEMA public FROM game_{sid}_rw;
```

返回连接串：

```
postgresql://game_{sid}_rw:<password>@<host>:<port>/<db>
  ?sslmode=require&options=-c%20search_path%3Dgame_{sid}
```

**要求**：

- R-DB-1：每个游戏**必须**拥有独立 schema 与独立 role，且 role 仅能访问该 schema。
- R-DB-2：游戏服务**必须**通过 PostgreSQL 协议直连（REST/PostgREST 仅暴露 `public`，不用于游戏库）。
- R-DB-3：连接串**必须**由平台生成，Agent 不得持有管理员凭证。

## 7. 发布态流程

### 7.1 发布

```
publish_game(name)                    # 由当前会话发起
 → 由 thread_id 解析 game_id
 → 运行构建与校验（见 7.4）
 → 打包工作区 → 对象存储 games/{game_id}/versions/{seq}.tar
 → 部署/更新托管服务 game-{game_id}
     · 注入环境变量：DATABASE_URL / PORT / NODE_ENV
     · 连接数据库所在网络；开启公网访问；配置健康检查
 → 写入 game_versions（seq+1，含 revision 与发布状态），更新 games.public_url（若首次）
 → 返回该版本公网链接
```

### 7.2 运行形态（必须：单服务同源）

- 一个游戏 = 一个托管服务，**同一服务**同时提供：静态前端、HTTP API、WebSocket。
- 游戏代码内部一律使用**相对路径**访问自身接口，保证同源、零配置。
- 单一公网链接对外。

### 7.3 版本

- 版本**只增不改**：每次发布产生一个不可变版本（seq+1），并生成托管平台的新 revision；发布结果内联在版本记录中。
- **当前在线版本** = 该游戏 `status='deployed'` 且 `seq` 最大的版本（派生，不落列）。
- `public_url` 跨版本稳定，属于游戏。
- 本期**不提供回滚**；历史版本产物保留留档。

### 7.4 发布前校验（必须）

- 产物存在且可构建成功。
- 服务监听约定端口，`/api/health` 返回正常。
- 源码中不得出现绝对域名、绝对端口、外部服务地址。
- 存在数据库迁移脚本（若使用数据库）。

## 8. 认证与授权

### 8.1 认证（CloudBase 身份认证）

- 前端通过 CloudBase JS SDK 登录（匿名或账号方式），SDK 自动维护 access_token 与 refresh_token。
- 请求携带 `Authorization: Bearer <access_token>`。
- 访问令牌为**标准 JWT**，关键声明：`iss` / `aud` / `sub`（用户 UID）/ `role` / `exp`。
- 后端**必须**在本地完成验签：

```
校验顺序：
  1) 通过 iss 获取 JWKS 公钥（带缓存，低频刷新）
  2) 验签（RS256）
  3) 校验 iss / aud / exp
  4) 取 sub 作为用户 UID
```

- R-AUTH-1：日常请求**不得**因验签而调用外部服务（公钥本地缓存即可）。
- R-AUTH-2：平台后端与 Agent 运行时**各自**独立验签，不得引入「由一方代验」的中转接口。

### 8.2 授权（平台侧）

- 认证解决「你是谁」，授权解决「你能做什么」，授权**必须**由平台后端实现。
- 归属校验：游戏归属 `games.owner_id`；会话经 `game_threads` 归属到游戏。
- 所有对游戏/版本/会话的操作**必须**校验其属于当前用户。

### 8.3 与游戏数据库的关系

- 游戏数据库使用独占 schema + 专属 role，**不使用** CloudBase 的数据库角色与行级权限体系。
- 身份认证仅用于平台用户身份，与游戏数据库权限解耦。

## 9. 接口契约

### 9.1 前端 → 平台后端（用户态）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/games` | 我的游戏列表 |
| POST | `/api/v1/games` | 新建游戏 |
| GET | `/api/v1/games/{game_id}` | 游戏详情（当前版本、部署链接） |
| GET | `/api/v1/games/{game_id}/versions` | 版本列表 |
| GET | `/api/v1/games/{game_id}/threads` | 会话列表 |
| POST | `/api/v1/games/{game_id}/threads` | 新建会话 |
| GET | `/api/v1/sessions/{thread_id}/preview` | 预览反代（HTTP + WebSocket） |

### 9.2 Agent 运行时 → 平台后端（内部）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/internal/sessions/ensure` | 由 `thread_id` 解析 `game_id`，创建/复用沙盒 |
| POST | `/internal/db/provision` | 开通游戏数据库，返回连接串 |
| POST | `/internal/games/publish` | 校验并发布，返回公网链接 |
| POST | `/internal/sessions/{thread_id}/server/restart` | 重启游戏服务 |

- 内部接口**必须**校验内部令牌；**不得**经由浏览器暴露。
- **不提供**「代验令牌」接口（见 R-AUTH-2）。

### 9.3 对话流式接口

- 前端使用 LangGraph SDK 连接 Agent 运行时，流式接收回复。
- 鉴权：携带同一 access_token，由 Agent 运行时本地验签。

## 12. 依赖管理

- Python 服务（`apps/api`、`apps/agent`）**各自独立**使用 `uv`，各自持有 `uv.lock` 与虚拟环境。
- 共享契约 `packages/contracts` 以**可编辑路径依赖**被两个服务引用：

```toml
[tool.uv.sources]
contracts = { path = "../../packages/contracts", editable = true }
```

- R-DEP-1：**不使用** uv workspace（父子工程）。原因：workspace 仅提供一个共享虚拟环境与共享锁，不提供成员间依赖隔离，且强制统一 Python 版本；本项目两个服务依赖栈差异大、独立部署，需要隔离。
- Node 侧（`apps/web`、`packages/game-template`）各自使用 `npm`。

## 13. 里程碑与验收

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| M1 沙盒链路 | 建立沙盒；后台运行游戏服务；沙盒内浏览器打开；NoVNC 同源反代嵌入 | 可见画面、可操作、外部 CDP 可操作同一浏览器 |

| M3 身份认证 | 前端登录；api/agent 本地验签 | 有效令牌可访问；无/错令牌被拒；得到正确 UID |
| M4 数据库 | 开通游戏 schema 与 role | 游戏服务可读写自身 schema；访问其它 schema 被拒 |
| M5 生成闭环 | 多轮对话生成带服务端的游戏 | 能在预览中游玩；会话结束后工作区保持 |
| M6 发布闭环 | 发布工具部署到托管 | 公网链接可打开、可玩、可访问自身数据库 |
| M7 版本 | 版本历史列表 | 能看到每次发布记录与当前在线版本 |
