## 0. 结论速览（先看我判断的）

1. **老项目的抽象分层可以直接延续**，只换底层实现：`Agent 编排`、`沙盒网关`、`存储网关`、`发布网关` 四类边界不变。
2. **腾讯云 Agent Sandbox（AGS）兼容 E2B SDK**，且提供 **All-In-One 沙盒**（代码执行 + Chromium + NoVNC 远程画面 + VSCode + WebShell）。它几乎是为本需求定制的：一个沙盒里同时跑「游戏后端 + 浏览器 + Agent 工具」。
3. **"浏览器渲染映射到产品前端"** 用 All-In-One 的 **NoVNC** 实现：产品前端嵌远程浏览器画面，用户在画面里操作，Agent 用 Playwright/CDP 操作**同一个浏览器**，所以"能看到 AI 操作"天然成立。
4. **数据库隔离**用 CloudBase PostgreSQL 的 **schema + 独立 role**：每局游戏一个 schema、一个只对该 schema 有权的 role，动态生成连接串。CloudBase 的 REST/PostgREST 只暴露 `public`，所以生成的后端必须走 **Postgres 协议直连**（云托管支持 VPC 内网直连）。
5. **发布**：后端用 **CloudBase 云托管（CloudRun）**，前端由同一个服务同源托管（推荐），或前端单独进**静态托管**。发布=平台侧调腾讯云 tcb API，Agent 不接触任何云凭证。
6. **地域已确认可行**：AGS 支持上海，CloudBase 默认上海、云托管也仅上海，三者可同落上海。AGS 沙盒开发态连 PG 走公网 SSL（需实测），发布后的云托管走同环境内网。
7. 最小闭环建议先支持**"带 Node 后端的游戏"**（哪怕单人也走服务端），因为需求明确要求"游戏后端运行在沙盒内 / 后端要部署"。

## 1. 老项目理解

### 1.1 需求（MVP）

非技术用户用中文描述玩法 → Agent 追问 → 生成可玩游戏 → 右侧试玩 → 多轮迭代 → 一键发布公网链接。
关键非功能：**隔离**（生成代码在沙盒跑）、**密钥不出后端**、**校验门禁**（不合格不发布）、**成本**（沙盒用完即毁）、**会话持久**（隔天可续）。

### 1.2 技术栈（现状）

| 层 | 老项目选型 | 关键位置 |
|---|---|---|
| 平台前端 | Next.js 15 + React 19 + `@langchain/langgraph-sdk` | `docs/agent-chat-ui`（参考）、`frontend/`（空） |
| Agent 编排 | LangGraph Server + **deepagents**（graph 工厂按 `thread_id` 装配） | `services/agent_server` |
| Agent ↔ 沙盒 | deepagents `BaseSandbox` 子类 `ModalBackend`（exec + 文件读写） | `agent/infra/modal_backend.py` |
| 执行沙盒 | **Modal Sandbox**，命名镜像 `game-runner`（node22 + playwright + npm deps + skills + 模板） | `services/sandbox/`、`app/gateways/modal.py` |
| 业务后端 | FastAPI（唯一持云密钥） | `services/api_server` |
| 对象存储 | 自建 MinIO（S3 协议，`minio.gqt.plus`） | `app/gateways/minio.py` |
| 关系库 | 自建 Postgres 17（会话归属 `thread_owners`） | `app/models/` |
| 模型 | `init_chat_model`，env 可配（老配置为 commandcode 网关上的 deepseek） | `agent/infra/model.py` |
| 可观测 | LangSmith | env |
| 游戏引擎 | Phaser 4.2.1，esbuild 打**单文件** `dist/index.html` | `services/sandbox/assets/templates/single/` |
| 联机参考 | 斗地主（回合制）、枪战（实时 30Hz），Node + Socket.IO | `docs/test-game`、`docs/test-game-2` |

### 1.3 老项目的关键机制（要迁移的资产）

- **沙盒目录契约**：`/workspace/work`（唯一可写）、`/workspace/input`（只读素材）、`/skills`（Phaser 技能库）、`/opt/deps`（依赖），`node_modules` 是指向 `/opt/deps` 的软链（避免快照把依赖上传）。
- **工作区持久化**：run 正常结束 → `aafter_agent` 中间件 → 增量快照 `work/` 到 MinIO `threads/{tid}/work` + `manifest.json`；`ensure` 时按 manifest 全量恢复。
- **发布**：Agent 在沙盒 `npm run build` → 调 `publish_single_game` 工具 → api_server 读 `dist/index.html` → 校验（体积/UTF-8/无外链/有内联脚本）→ 落 MinIO `games/{tid}/index.html`（公开读）→ 返回公网链接。
- **鉴权边界**：浏览器只拿短期 token；api_server 持全部云密钥；Agent 只有沙盒操作权 + 内部接口（`X-Internal-Token`）。
- **多轮记忆**：LangGraph checkpointer（Postgres），`thread_id` 串全场。

### 1.4 老项目暴露的问题（新方案要解决的）

1. 生成一轮 **20 分钟以上**，80% 花在 Agent 自测 —— 需要更克制的提示词 + 平台侧校验。
2. 发布产物只有**单文件静态 HTML**，无法承载后端/数据库/联机。
3. 公网托管是一次性 MinIO 链接，**没有发布体系**（版本、回滚、遥测、实例管理）。
4. 用户体系未落地（publish 用 mock user）。
5. Agent 可改构建脚本/骨架（沙盒 root），门禁不可信。

## 3. 开发阶段架构（核心）

### 3.1 目标形态

```
┌───────────────────────────── 产品前端（浏览器） ─────────────────────────────┐
│  左：对话/审批流          右：沙盒画面（NoVNC/VNC 流）                          │
│      │                        ▲ 鼠标键盘事件                                  │
└──────┼────────────────────────┼──────────────────────────────────────────────┘
       │ SSE / WebSocket        │ iframe / WebSocket（可经平台代理，同源）
       ▼                        │
┌──────────────┐  内部接口   ┌──┴───────────────────────────────────────────┐
│ api_server    │◀───────────▶│ agent_server（LangGraph）                     │
│ 会话/发布/DB   │             │  deepagents + tools + skills                  │
└──────┬───────┘             └──────────────┬───────────────────────────────┘
       │ 管控面(tcb API)                     │ E2B SDK（AGS）
       ▼                                     ▼
┌──────────────┐              ┌──────────────────────────────────────────────┐
│ CloudBase     │              │ AGS 沙盒（每 thread 一个，All-In-One 镜像）     │
│ · PostgreSQL  │◀───直连PG────│  · 游戏后端（Node，监听到 0.0.0.0:PORT）        │
│ · 云存储 COS   │              │  · Chromium（打开 localhost:PORT）             │
│ · 云托管       │              │  · NoVNC(:9000/novnc) ◀── Agent 用 CDP 操作    │
│ · 静态托管     │              │  · /workspace/work、/skills、shell/文件工具     │
└──────────────┘              └──────────────────────────────────────────────┘
```

### 3.2 一次「生成 + 预览」时序

```
用户: "做个打砖块"
 → 前端 api_server /sessions/ensure → 平台创建/复用 AGS 沙盒（每 thread 一个）
 → 前端 langgraph 连 agent_server，run(thread_id)
 → Agent 在沙盒 shell 里写代码（/workspace/work）
 → Agent 启后端：npm start（后台进程，监听 PORT）
 → Agent 用沙盒内 Chromium 打开 http://localhost:PORT 自测
 → 产品前端右栏嵌入 NoVNC → 用户实时看到并可直接操作
 → 用户反馈 → Agent 改代码 → 热重启后端 → 画面刷新
```

### 3.3 "渲染映射" 的两种实现

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 远端浏览器画面（已选）** | 前端嵌入 AGS All-In-One 的 NoVNC（`/novnc/vnc_lite.html?access_token=...`），浏览器在沙盒内 | 用户操作 + 看 Agent 操作**同一个浏览器**，完全满足需求 | 像素流带宽/延迟；iframe 的 CSP/X-Frame 需处理（**建议平台反代同源**） |
| B. 沙盒公网 URL 直连（备选/兜底） | `sandbox.get_host(PORT)` 拿公网地址，前端 iframe 直接玩 | 延迟最低、最省资源 | Agent 的浏览器是"另一个客户端"，用户看不到 Agent 画面；跨域/Cookie 问题 |

> **已选 A**。落地要点：NoVNC URL 带 `access_token`，不能直接暴露给浏览器也不便跨域 iframe → 由 **api_server 反代**成平台同源路径（如 `/api/v1/sessions/{thread_id}/preview`），前端用同源 iframe 嵌入；VNC 的 websockify 走 WebSocket 也要一并反代。若画面延迟影响游玩，可在 A 之上叠加 B：画面用于观察 + 直连 URL 用于实际操作。

### 3.4 Agent 与沙盒的对接

- AGS 是 E2B 兼容 → 直接用 `e2b` SDK（`E2B_DOMAIN=ap-guangzhou.tencentags.com` + `E2B_API_KEY`）。
- 把老项目的 `ModalBackend` 换成 **`E2BSandboxBackend`**（同样实现 deepagents `BaseSandbox` 的 `execute` / `upload_files` / `download_files`），改动量很小。
- **镜像**：两种路线
  - 路线 1（快）：直接用官方 **All-In-One** 沙箱工具，运行时把 `/skills` 和工程模板写进 `/workspace/work`。
  - 路线 2（稳）：用 **envd 自定义镜像**（腾讯云文档 1814/137275）把 node/phaser 依赖/skills/模板/Chromium 全部烘进镜像，控制台登记为沙箱工具；对应老项目的 `services/sandbox/build.py`。
- AGS 支持 **pause/resume** 与 **Persistent**，可替代"闲置销毁 + 快照恢复"的复杂逻辑（但成本模型不同，见 §8）。

## 4. 数据库隔离设计（用户明确要求）

### 4.1 分层

| 库/域 | 用途 | 访问者 |
|---|---|---|
| CloudBase PG 的 `platform` schema | 线程归属、游戏登记、版本、部署记录、DB 租约 | api_server（平台 role） |
| CloudBase PG 的 `game_<sid>` schema | **每个游戏独占**，放游戏自己的表 | 游戏后端（专属 role） |

> CloudBase PG 的 REST/PostgREST **只暴露 `public` schema**，所以游戏后端必须用 **Postgres 协议直连**（云托管内网可达），schema 隔离才成立。若未来想用 SDK/REST 直连，则隔离要改成 `public` + RLS（按 `owner_id`），而不是 schema。

### 4.2 动态开通（平台工具，Agent 触发）

Agent 调平台工具 `provision_game_database()`，平台侧以管理员身份执行（`ExecutePGSql` 或 admin 直连）：

```sql
CREATE SCHEMA IF NOT EXISTS game_<sid>;
CREATE ROLE game_<sid>_rw LOGIN PASSWORD '<随机强密码>';
GRANT USAGE, CREATE ON SCHEMA game_<sid> TO game_<sid>_rw;
GRANT ALL ON ALL TABLES    IN SCHEMA game_<sid> TO game_<sid>_rw;
GRANT ALL ON ALL SEQUENCES IN SCHEMA game_<sid> TO game_<sid>_rw;
ALTER DEFAULT PRIVILEGES IN SCHEMA game_<sid>
  GRANT ALL ON TABLES    TO game_<sid>_rw;
ALTER DEFAULT PRIVILEGES IN SCHEMA game_<sid>
  GRANT ALL ON SEQUENCES TO game_<sid>_rw;
-- 关键：收回对 public 的权限（确保越不出去）
REVOKE ALL ON SCHEMA public FROM game_<sid>_rw;
```

返回连接串（仅能进该 schema）：

```
postgresql://game_<sid>_rw:<pw>@<host>:<port>/<db>
  ?sslmode=require&options=-c%20search_path%3Dgame_<sid>
```

隔离保证：
1. **schema 级**：role 只有 `game_<sid>` 的 usage/create，`public` 被 revoke。
2. **role 级**：独立账号、随机密码，不复用平台 role。
3. **动态化**：连接串由平台在开通时生成并写入沙盒 `.env`；发布时由平台注入云托管环境变量。
4. **凭证归属**：Agent 只拿到"本游戏这一份"连接串，拿不到管理员凭证；发布后仍用同一份（或重新签发）。

### 4.3 平台元数据表（建议）

```
thread_owners(thread_id, user_id, ...)          -- 沿用
games(game_id, thread_id, name, status, ...)
game_versions(game_id, version, created_at, ...)
game_deployments(game_id, service_name, url, revision, status, ...)
game_databases(game_id, schema_name, role_name, secret_ref, ...)
```

## 5. 发布阶段设计

### 5.1 产物形态（已定：单 CloudRun 服务同源）

老项目的核心原则是 **"同源零配置"**（游戏内一律相对路径）。因此推荐：

- 一个游戏 = 一个 CloudRun 服务，**同一个 Node 服务同时提供**：静态前端（Phaser 打包产物）、HTTP API、WebSocket。
- 只有一个公网 URL（`<service>-<env>.webapps.tcloudbase.com` 或 CloudRun 默认域名），天然同源，Socket.IO 的 `/socket.io/` 不折腾。
- 若坚持"前端进静态托管"：则前端 `xxx.tcloudbaseapp.com` + 后端 `yyy.tcloudbase.com`，跨域 + WSS 到后端 + 运行时注入后端地址，MVP 复杂度明显上升。**建议 MVP 同源，后续把纯静态单人游戏再拆静态托管/CDN。**

### 5.2 发布流程（Agent 调工具 → 平台执行）

```
Agent: publish_game()
 → 平台内部接口 POST /internal/games/publish {thread_id}
 → 1) 沙盒内构建（npm run build），平台**重新校验**产物
 → 2) 若有数据库需求：确保 game_<sid> schema + role 已开通
 → 3) 打包代码包 → 调 tcb API 部署 CloudRun 服务（源码/镜像）
      · 注入 env：DATABASE_URL（该游戏专属）、PORT、NODE_ENV
      · 配 VPC（内网连 PG）、公网访问、健康检查
 → 4) 落 game_deployments，返回公网 URL
```

### 5.3 安全

- Agent **不持**任何云凭证/Provider 凭证，只能请求平台 API。
- 生成的前端代码是**陌生人代码**：CloudRun 侧限并发/超时/内存，DB role 最小权限，禁止访问平台 schema。
- 发布前校验（沿用老项目思路）：结构、体积、无外链、必须包含健康检查/优雅退出（模板保证）。

## 8. 风险与待验证

1. **地域**：~~待确认~~ → 已确认 AGS 支持上海、CloudBase 与云托管均在上海，**统一上海**。剩余待实测：AGS 上海是否有 All-In-One 工具；沙盒公网直连 CloudBase PG 的 SSL/延迟。
2. **沙盒直连 CloudBase PG**：沙盒出口 IP 不固定，无法用 IP 白名单；需 SSL + 强密码 + 仅 schema 权限，或经平台代理。需实测。
3. **NoVNC 嵌入**：`X-Frame-Options`/CSP、access_token 泄露、跨域反向代理，需要平台同源反代。
4. **NoVNC 延迟/音频**：像素流对实时游戏（30Hz）体验有限，可能需要 WebRTC 方案。
5. **All-In-One 能力边界**：CDP 端口、能否常驻后端进程、端口是否随 `get_host` 暴露，需要实测（官方文档偏代码执行，进程托管要验证）。
6. **CloudRun 部署任意生成代码**：滥用/资源/费用风险，需要配额与审核。
7. **Agent 一轮耗时**：老项目 20min+ 的教训，工具与提示词要收敛；浏览器自测要受限。
8. **AGS 配额/冷启动/镜像预热**：需查配额文档与预热接口。
9. **LangGraph Server on CloudRun**：长连接、checkpointer 用 CloudBase PG、是否需要 Redis，要验证。
10. **Phaser 多文件形态**：后端游戏不再需要"打单文件"，构建脚本与校验都要改。

## 12. 从零设计（不继承老项目代码）

> 以下才是真正的实现依据。老项目只提供"哪些坑踩过"的信息。

### 12.1 设计原则

1. **只做一种产物**：带 Node 后端的游戏服务。没有"单文件静态"这条分支，构建/校验/发布只有一条路。
2. **同源零配置**：游戏前端用相对路径调自己的后端，发布后天然同源（CloudRun 单服务）。游戏不认识平台。
3. **凭证不出平台**：Agent 只有沙盒操作权 + 平台内部接口；AGS API Key、tcb SecretId/Key、PG 管理凭证只在 api_server。
4. **框架用 deepagents，但要克制**：保留 deepagents + LangGraph Server 的既有能力；失败教训在"太多隐式机制 + Agent 过度自测"，所以自定义工具与中间件保持**少而显式**。
5. **沙盒无状态化**：沙盒随时可被回收，正确性只依赖 COS 快照；不依赖 pause/resume。

### 12.2 系统组成（5 块）

| api | FastAPI（云托管） | 平台控制面：沙盒编排、预览反代、DB 开通、发布、鉴权 |
| agent | LangGraph Server + deepagents（云托管） | 对话编排 + 工具调用 |
| sandbox | AGS（All-In-One，上海，挂载 COS） | 每 thread 一个开发环境 |
| cloudbase | 身份认证 + PG + COS + CloudRun + 静态托管 | 用户体系、数据、对象、发布运行时 |

### 12.4 Agent 设计（deepagents + LangGraph Server）

- 在 deepagents 内置工具之上，叠加少量自定义工具：

| 工具 | 作用 |
|---|---|

### 12.5 沙盒生命周期 + 托管持久化（AGS 存储挂载）

**不写任何快照代码**。AGS 原生把 COS 挂进沙盒，并用实例级 `SubPath` 做**每游戏**隔离（工作区属于游戏，不属于会话）：

```jsonc
// Tool 级：定义 COS 来源与默认挂载
"StorageMounts": [{
  "Name": "cos-games",
  "StorageSource": { "Cos": { "BucketName": "ai-game-xxx", "BucketPath": "/games" } },
  "MountPath": "/workspace/work",
  "ReadOnly": false
}]

// Instance 级：按游戏隔离
"MountOptions": [{
  "Name": "cos-games",
  "SubPath": "<game_id>",        // → COS /games/<game_id>
  "MountPath": "/workspace/work"
}]
```

- 效果：`COS ai-game/games/{game_id}` ⇄ 沙盒 `/workspace/work`。同一游戏的多个会话共用这份工作区；实例销毁后再用同一 `SubPath` 起实例，源码原样回来；删数据只在 COS 侧。
- 因此**删除**：`/internal/sessions/{tid}/snapshot`、tar 逻辑、run 结束自动快照中间件的存储部分。
- `node_modules` **不进挂载层**：依赖平台固定，**烘进沙盒镜像**；挂载层只放源码。
- 素材可选：另挂一个只读 COS 子路径到 `/workspace/input`（同一套配置模型）。
- 沙盒超时自毁即可，无需 destroy hook。
- **待实测**：COSFS 的 POSIX 行为（symlink/rename）；若对开发不友好，同配置换成 **CFS** 挂载。

### 12.6 数据库开通

- 平台工具 `provision_database` → api_server 用管理员凭证执行：建 `game_<sid>` schema + 专属 role，只授该 schema，`REVOKE public`，返回 `postgresql://...?options=-c search_path%3Dgame_<sid>`。
- 连接串写入沙盒 `/workspace/work/.env`；发布时由平台注入云托管环境变量。
- 生成的后端一律 `pg` 直连（REST/PostgREST 只暴露 public，不参与）。

### 12.11 认证（CloudBase 身份认证）

**心智模型**：CloudBase 是**身份发行方（IdP）**，我们的后端是**资源服务器（只验不签）**。这是标准 OIDC 的 issuer / resource-server 分离；**认证外包，授权留在后端**。

- 前端：`@cloudbase/js-sdk` `init({ env, accessKey: <Publishable Key> })` → 登录（匿名/密码/短信/微信/自定义）→ SDK 自动维护 access_token(2h) / refresh_token(30d)。
- Token 是标准 JWT，关键 claims：`iss = https://<envId>.api.tcloudbasegateway.com/auth/v1`、`aud = <envId>`、`sub = UID`、`role`、`exp`。
- 后端校验（推荐路线 1）：
  1. **本地 JWKS 验签**：取 CloudBase OIDC/JWKS 公钥（由 `iss` 推导，形如 `<iss>/.well-known/jwks.json`，实现时确认），本地验 RS256 + 校验 `iss/aud/exp` → 取 `sub` 作 UID；公钥缓存。**日常请求零外呼**，仅低频刷新公钥或做用户管理时才访问 CloudBase。
  2. **HTTP 网关身份认证**：路由级开关，网关先验、未过直接挡；后端读注入的身份。适合粗粒度。
- 后端分工：
  - `apps/api`：验签 → `uid = sub` → 业务授权（thread 归属、发布权限，即老项目的 `check_owner`）。
  - `apps/agent`：LangGraph auth hook 同样验签 → identity = sub。
  - 生成的游戏后端：可选，同一 JWT 验签得到玩家 UID。
- **与游戏 DB 的关系**（重要）：游戏库走直连 + 专属 schema/role，**不使用** CloudBase 的 `anon/authenticated/service_role`，也不走 RLS；CloudBase auth 的 `role` 只在经网关访问 `public` schema 时生效。两套体系互不干扰。
- 待确认：CloudBase OIDC/JWKS 具体端点；匿名账号跨设备/清缓存的 UID 变化（需引导「账户关联」升级）。

### 12.12 领域模型（用户 / 游戏 / 会话 / 版本）

关系：**用户 1—N 游戏；游戏 1—N 会话；游戏 1—N 版本**。

**由此推出一条关键结论**：工作区（沙盒 + COS 挂载）与数据库 schema 都以**游戏**为隔离单位，**不是会话**。会话只是"针对某个游戏的一次对话"，同一游戏的多个会话编辑同一份代码。

```
platform.users
  user_id     varchar(64) PK   -- CloudBase UID（JWT sub）
  nickname    text
  created_at, updated_at

platform.games
  game_id       uuid PK
  owner_id      varchar(64) → users
  name          text
  status        text            -- active | archived
  current_version_id uuid null
  db_schema     text            -- game_<short>
  created_at, updated_at

platform.game_threads
  thread_id     uuid PK         -- LangGraph thread_id
  game_id       uuid → games
  created_by    varchar(64) → users
  title         text
  status        text            -- active | archived
  created_at, updated_at

platform.game_versions
  version_id    uuid PK
  game_id       uuid → games
  seq           int             -- 每游戏递增 1,2,3…
  source_thread_id uuid → game_threads
  note          text
  status        text            -- building | live | failed | superseded
  artifact_key  text            -- COS 代码包留档
  created_at

platform.game_deployments
  deployment_id uuid PK
  game_id       uuid → games
  version_id    uuid → game_versions
  service_name  text            -- CloudRun 服务名 game-{game_id}
  revision      text            -- CloudRun 版本
  public_url    text
  status        text
  created_at, updated_at

platform.game_databases
  game_id     uuid PK → games
  schema_name text
  role_name   text
  secret_ref  text
  created_at
```

| 对象 | 老项目 | 新 |
|---|---|---|
| 沙盒名 | `game-{thread_id}` | `game-{game_id}`（每游戏一个活跃沙盒） |
| COS 工作区 | `threads/{thread_id}/work` | `games/{game_id}/work`（挂载 `SubPath=game_id`） |
| 归属 | `thread_owners` | `games.owner_id`（会话经 `game_threads` 归属） |
| 版本 | 无（固定 key 覆盖） | `game_versions` 不可变 + `current_version_id` 指针 |
| 部署 | 无 | 一游戏一 CloudRun 服务，版本 = CloudRun revision |

**并发**：同一游戏多个会话同时改代码会冲突。需定策略（下一步确认）：
- (a) 单活跃会话：游戏同一时刻只允许一个 run，其余只读/排队（最简单）；
- (b) 游戏级锁：run 期间对 `game_id` 加锁，串行写。
倾向 (b)：`modal.locked` 那套换成按 `game_id` 的锁即可。

**主要流程**：
- 新建游戏：创建 `games` + 第一个 `game_threads`；首轮生成后填 `name`。
- 继续游戏：在已有 `games` 下新建 `game_threads`，复用同一工作区/沙盒。
- 发布：Agent 调 `publish_game` → 平台由 `thread_id` 解析 `game_id` → 校验 → 建 `game_versions`（seq+1）→ 部署/更新 `game-{game_id}` 服务 → 更新 `current_version_id` 与 `game_deployments`。
- 回滚：把 `current_version_id` 指回旧版本并重新部署（或用 CloudRun 流量切换）。

**前端所需的平台 API（示意）**：
```
GET  /api/v1/games                     # 我的游戏列表
POST /api/v1/games                     # 新建游戏（可带首个会话）
GET  /api/v1/games/{game_id}           # 游戏详情（当前版本、部署 URL）
GET  /api/v1/games/{game_id}/versions  # 版本列表
POST /api/v1/games/{game_id}/versions/{v}/rollback
GET  /api/v1/games/{game_id}/threads   # 会话列表
POST /api/v1/games/{game_id}/threads   # 新建会话
GET  /api/v1/sessions/{thread_id}/preview  # NoVNC 反代
```

### 12.13 Python 依赖管理：两个服务独立，契约包用 path 依赖

**结论：不为 api/agent 建 uv workspace（父子工程）。**

> **uv workspace 到底解决什么**：它解决的是"**多个同呼吸的包共享同一个依赖世界**"——单 `uv.lock` 保证彼此依赖版本一致、成员间 `{ workspace = true }` 即改即用、统一 `requires-python`、一条 `uv sync` 装齐。典型适用：一个产品在 monorepo 里拆出的若干**紧密耦合、一起演进/一起发布**的库与应用（如 Cargo workspace 那种）。**不适用**：依赖栈不同、各自独立部署、需要各自 venv 的服务。
>
> 注意 **workspace ≠ monorepo**：monorepo 是目录形态，workspace 只是其中一种依赖管理方式；"独立项目 + path 依赖"同样是合法的 monorepo。

原因（uv 官方语义）：

- workspace **只有一个共享 venv（根 `.venv`）和一个 `uv.lock`**，不给每个成员单独建 venv；
- **没有依赖隔离**：官方明确"uv 无法保证一个成员不去 import 另一个成员的依赖"，容易出现"本地能跑、部署镜像缺包"；
- **全 workspace 强制单一 `requires-python`**（取所有成员的交集）；
- 成员依赖一旦冲突，整个 `uv lock` 失败，两个服务的升级互相拖累。

api（FastAPI / SQLAlchemy / psycopg / COS SDK）与 agent（LangChain / LangGraph / deepagents / E2B）依赖差异大、且分别部署，正是官方说的"不适合 workspace"的情形。

做法：各自独立项目，各有 venv 与 lock：

```
apps/api/pyproject.toml     + apps/api/uv.lock     + apps/api/.venv
apps/agent/pyproject.toml   + apps/agent/uv.lock   + apps/agent/.venv
packages/contracts/         # 普通可安装包（Pydantic 模型）
```

共享契约用可编辑 path 依赖：

```toml
# apps/api 与 apps/agent 各自
[tool.uv.sources]
contracts = { path = "../../packages/contracts", editable = true }
```

- 每个服务在自己目录 `uv sync`，venv/lock/部署镜像完全隔离；Docker 就地构建。
- 共享依赖（pydantic / httpx）可能漂移：在 `packages/contracts` 钉死版本范围即可缓解。
- 若将来确实想统一，再评估 workspace；当前不建议（workspace 不会给成员多个 venv）。
