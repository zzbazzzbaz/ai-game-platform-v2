# 01 · 项目背景、目标与决策记录

## 1. 产品是什么

面向**无编程基础**的用户：用自然语言与 AI 多轮对话，生成一个**带服务端的可玩游戏**，在平台内实时预览与调试，并**一键发布到公网**，通过链接分享给他人游玩。

## 2. 最小技术闭环（本期目标）

1. 用户注册 / 登录，创建 / 进入一个游戏。
2. 用户与 AI 多轮对话，AI 在云端沙盒中编写并运行该游戏的代码（Node 后端 + Phaser 前端）。
3. 平台前端实时展示沙盒内浏览器的画面，用户可直接操作，同时能看到 AI 的操作。
4. 游戏若需要持久化，使用平台分配的独占数据库（每游戏独立数据库 + 专属 role）。
5. AI 调用发布工具，把该游戏部署到云端，返回公网可玩链接。

## 3. 范围外（本期不做）

- 游戏大厅、社交分享、评论。
- AI 生成图片 / 音频素材。
- 视觉模型自动试玩与自动修复闭环。
- 多用户协作编辑同一游戏。
- 游戏间的数据互通。

## 4. 术语

| 术语 | 含义 |
|---|---|
| 游戏（game） | 生成项目的单位；有独立工作区、沙盒、数据库、托管服务 |
| 会话（thread） | 同一游戏下的多轮对话；同一游戏的多个会话共享同一工作区 |
| 沙盒（sandbox） | AGS 实例：运行游戏服务 + 内置 Chromium + NoVNC |
| 工作区（work） | 沙盒内 `/workspace/work`，实时落 COS，天然持久化 |
| 素材（input） | 沙盒内 `/workspace/input`，只读，来自 COS |
| 预览 | 前端 iframe 嵌入沙盒 NoVNC；用户与 AI 操作同一个 Chromium |
| 发布 | 把工作区代码部署为 CloudRun 服务，返回公网链接 |
| `sid` | `game_id` 去掉 `-`（32 位十六进制），用于派生数据库名等资源名 |

## 5. 决策记录

### 5.1 早期决策（架构讨论定案）

| 编号 | 决策 | 说明 |
|---|---|---|
| D1 | 预览 = NoVNC（WebRTC 为备选）映射到前端右栏 | 用户与 AI 看同一浏览器画面 |
| D2 | 发布 = 单服务同源（静态前端 + HTTP API + WebSocket） | 一个游戏 = 一个托管服务 = 一个公网链接 |
| D3 | Agent = deepagents + LangGraph Server | 保留现成编排与工具能力 |
| D4 | 首个游戏形态：单人，但带 Node 后端 | 打通"前端 + 后端 + 数据库"全链路 |
| D5 | 地域：全部上海；自建 PG 选上海相近节点 | 低延迟 |
| D6 | 沙盒镜像：AGS `aio` 预置类型 | 无需自建镜像；后期可定制以加速冷启动 |
| O1 | 沙盒持久化 = AGS 原生 COS 存储挂载 + 实例级 `x-mounts` subPath | 实时落 COS，无需自研同步 / 快照 |
| O2 | Agent 零云凭证；一切管理动作经平台后端 | Agent 只调平台内部接口 |
| O3 | 发布由 Agent 调平台工具触发 | Agent 不直接调云 API |

### 5.2 技术栈定案（A1，2026-10-02）

**A1 = 自建认证 + 自建 PostgreSQL（VPS）；CloudBase 仅保留云托管；`apps/api`、`apps/agent`、平台前端部署在自建 VPS。**

| 组件 | 归属 |
|---|---|
| `apps/api`、`apps/agent`、平台前端 | 自建 VPS（Docker + Nginx 反代） |
| 平台数据库（元数据 + 每游戏独立库） | 自建 PostgreSQL（VPS，与 api 同机 / 同内网） |
| 身份认证 | 自建（平台签发 / 校验 JWT，RS256 + 平台 JWKS） |
| 发布出去的游戏服务 | CloudBase 云托管（CloudRun） |
| 对象存储（工作区 / 素材 / 版本包） | 腾讯云 COS **独立桶**（与 AGS StorageMount 同一个桶） |
| 开发沙盒 | 腾讯云 AGS（每游戏一个） |

**弃用 CloudBase 认证与 CloudBase PG 的原因**（调研存档见《03-验证结论与坑》§5）：

- CloudBase PG **无法 `CREATE ROLE`**（权限 42501）→ 做不了"每游戏独立 role"；
- **AGS 沙盒无法直连 CloudBase PG**（两者不在同一网络）；
- CloudBase 网关与 tcb-api 是**两套签名域**，自定义登录 token 不被 REST 数据面接受；
- 结论：只有**自建 PG** 才能同时满足"每游戏独立库 / role + 沙盒与托管直连"。

### 5.3 后续决策（2026-10-08，实测后）

| 编号 | 决策 | 说明 |
|---|---|---|
| A1.1 | 隔离单位 = **每游戏独立数据库** `game_{sid}` + role `game_{sid}_rw`；平台元数据独立库 `aigame_platform` | 实测可行；比 schema-per-game 隔离更强。开通**必须** `REVOKE CONNECT … FROM PUBLIC` |
| A1.2 | 预览分阶段：开发期**直接 iframe 嵌 NoVNC**（URL 含 token）；同源反代列为**上线前**安全加固 | 实测无 `X-Frame-Options` / CSP；多用户安全后期处理 |
| A1.3 | M3 自建认证**不单独验证** | 标准方案（RS256 + JWKS），随 `apps/api` 实现一并验收 |
| A1.4 | VPS PG **暂不启用 SSL** | 已知风险；**上线前必须**启用并改 `sslmode=require`（见《04》Q1 / Q8） |
| A1.5 | 数据模型精简：无 `user_sessions`（无状态 JWT）、无 `users.role`、无 `game_databases`（开通为幂等副作用） | 见《02》§5 |
| A1.6 | 验证用测试资源保留（CloudRun 服务 `api-deploy-probe`、库 `game_apideploy_probe`） | 见《05-资源与凭据》§8 |

## 6. 硬性约束

- 正式项目**不得引用旧项目**（`2026.9/AI游戏平台`）的代码与资料；本目录文档是唯一依据。
- 平台生成的游戏代码视为**不可信**：不得接触平台凭证，只能读平台注入的环境变量。
- **管理员凭证只在 `apps/api`**；Agent、沙盒、游戏服务都不持有云端管理凭证。
- 发布出去的游戏服务与其数据库**同源隔离**：只持自身 `DATABASE_URL`。
