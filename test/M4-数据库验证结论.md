# M4 数据库验证结论

- 日期：2026-10-02
- 范围：**AGS 沙盒 → CloudBase PostgreSQL 直连**（M4-1）及建 schema/role 能力
- 结论：**沙盒直连 PG 不可行**；CloudBase PG 的正确用法是 **PostgREST + JWT + RLS（HTTP）**。**无法创建每游戏 role**（42501）。

> **后续决策（2026-10-02）**：平台最终选择 **A1 —— 自建 PostgreSQL（VPS）+ 自建认证**（见 `docs/spec/技术架构规格.md` v0.2）。本文件作为 **CloudBase PG / RLS / 自定义登录的调研存档**；其中「CloudBase 无法建 role」「沙盒无法直连」「两套签名域/自定义登录黑盒」正是自建 PG + 自建认证的决策依据。

## 一、结论要点

1. **沙盒直连 PG：不可行**
   - PG 自身看到的是内网地址 `28.72.71.124:50733`；从 AGS 沙盒（PUBLIC 网络）TCP 该地址 → **UNREACHABLE**。
   - 直连需要控制台「账号管理」创建的登录账号 + 连接地址；官方也建议云函数/云托管走**内网/VPC**，而非公网。沙盒不在该 VPC。
2. **PostgREST HTTP API：可行且公网可达**（推荐）
   - 端点：`https://<envId>.api.tcloudbasegateway.com/v1/rdb/rest/<table>`
   - 认证头：`Authorization: Bearer <Publishable Key | access_token | API Key>`
   - 实测：**AGS 沙盒内** `GET /v1/rdb/rest/sb_probe` → **200**，返回数据。
   - 限制：**只暴露 `public` schema**（`auth`/`storage` 及其它 schema 不可经 REST 访问）。
3. **DDL 能力（云 API `ExecutePGSql`，实测）**
   - 无论 MCP 还是管理员子账号直调，均以 **`cloudbase_postgres`**（非 super）执行；
   - ✅ `CREATE SCHEMA`、`CREATE TABLE`、`GRANT`、`INSERT` 等可用；
   - ❌ **`CREATE ROLE` 被拒**：`permission denied to create role (SQLSTATE 42501)`，用 `DO $$` 包装亦同。
   - 角色现状：`anon/authenticated/service_role` 均 `NOLOGIN`（仅经 JWT 使用）；无 superuser；仅 dashboard 角色有 CREATEROLE，但不可用。

## 一之补充：关于「把沙盒加入 VPC」

- **AGS 支持 VPC 模式**：`NetworkMode: VPC` + `VpcConfig.{SubnetIds,SecurityGroupIds}`，可把沙盒放进你账号的 VPC（如默认 `vpc-ad1ieah8`）。
- **但 CloudBase PG 不在你的 VPC 里**：它是 CloudBase 托管的**共享**实例（`postgres-5s8d8ijw`，`TenantType=SHARED`）；**账号下标准 PostgreSQL 实例列表为 0**（`tccli postgres DescribeDBInstances` → TotalCount=0）。
- 因此，把沙盒放进你的 VPC **仍然连不到 PG**；跨网络需要 CloudBase 的「内网互联/资源互联」，而**共享实例基本不会开放到你的 VPC**。
- 此外，直连还需要**一个登录账号**（内置 `anon/authenticated/service_role` 均为 `NOLOGIN`，需控制台「账号管理」创建）与**每游戏 role（建不了）**。

→ 结论：对当前共享实例，**"沙盒进 VPC 直连"这条路走不通**；方案 A（PostgREST + JWT + RLS）是可行且顺路的选择。

|---|---|---|
| 沙盒→PG 直连 | 沙盒内 `nc`/`/dev/tcp 28.72.71.124:50733` | **UNREACHABLE** |
| 沙盒→PostgREST | 沙盒内 `curl -H "Authorization: Bearer <pk>" …/v1/rdb/rest/sb_probe` | **200** + 数据 |

## 二·2、RLS 隔离与 public-only 实测（2026-10-02）

用一张 `public.rls_probe(id, game_id, secret)` + RLS 策略 `USING (game_id = auth.uid())` 做端到端验证：

| 身份 / 通道 | 结果 | 说明 |
|---|---|---|
| REST + Publishable Key（`sub=anon`, role=anon） | 仅 `game_id='anon'` 行 | **RLS 在公网 REST 生效** |
| REST + `service_role` API Key | **全部 3 行** | `service_role` `BYPASSRLS`（仅供平台后端） |
| REST 无凭证 | **401** `MISSING_CREDENTIALS` | |
| DB `Role=authenticated` + claims `sub=gameA` | 仅 `gameA` 行 | 任意游戏身份隔离成立 |
| DB `Role=authenticated` + claims `sub=gameB` | 仅 `gameB` 行 | **跨游戏不可见** |
| DB `Role=authenticated` 无 claim | 0 行 | 无身份即无数据 |

**public-only（PostgREST 暴露范围）**：

| 请求 | 结果 |
|---|---|
| `GET /v1/rdb/rest/hidden_probe`（表只建在 `probe_schema`） | **404**（在 `public` 里找不到） |
| 同上 + `Accept-Profile: probe_schema` | **406** `Invalid schema: probe_schema` |
| `service_role` 访问非 public 表 | 仍 **404** |

**结论**：

- 方案 A 的隔离**可通过 RLS 落地**：令牌的 `sub` 决定可见行，跨游戏不可见；`service_role` 可全量。
- **PostgREST 只暴露 `public`**，非 public schema **无法**经公网 REST 访问（与官方文档一致）。
- 因此**游戏后端必须持有一个 `sub=game_{sid}` 的令牌**（建议 CloudBase 自定义登录）才能让 RLS 按游戏隔离；若给游戏发 `service_role` API Key，则隔离失效（可读写全部数据）。

## 二·3、游戏身份令牌签发（2026-10-02）

目标：让游戏后端拿到一个 `sub` 唯一标识「本游戏」的令牌，用于驱动 RLS。

**发现 1：环境有两套签名密钥 / 两个认证域**

| 域 | JWKS `kid` | 作用 |
|---|---|---|
| 网关 `api.tcloudbasegateway.com` | `f76b0310…`、`5af1590d…` | **REST 数据面**；Publishable Key、匿名令牌在此 |
| `ap-shanghai.tcb-api.tencentcloudapi.com` | 9 把（含自定义登录 token 的 `6627c0d2…`） | OIDC / **自定义登录**在此 |

→ 网关 REST **只认网关签发的令牌**；tcb-api 签的令牌会被拒。

**发现 2：自定义登录可用，但 token 进不了 REST 数据面**

- 自定义登录流程：服务端用私钥签 Ticket（`<private_key_id>/@@/<JWT>`，payload `uid`），`POST /auth/v1/signin/custom` 换取 token。
- 在 **tcb-api** 域登录成功，token `sub = gameA`（精确等于自定义用户 ID，4–32 字符）。
- 但：
  - 拿该 token 调**网关 REST** → **`401 ACCESS_TOKEN_KID_INVALID`**（网关不认 tcb-api 的签名密钥）；
  - 该 token **没有 `role` claim**，PostgREST 无法确定角色；
  - 在**网关**域做自定义登录 → `400 私钥已过期或私钥不存在`（MCP 生成的密钥未注册到网关侧）。

**发现 3：网关匿名登录可用，REST 隔离实测通过**

- `POST {gateway}/auth/v1/signin/anonymously`（需 `x-device-id`）→ 网关签名 token，`role=anon`，`sub` 唯一。
- 实测（表 `public.rls_probe` + 策略 `TO anon USING (game_id = auth.uid())`）：

| 令牌 | REST 结果 |
|---|---|
| anon#1（`sub=B11l…`） | 仅 `game_id=B11l…` 行 |
| anon#2（`sub=_dFH…`） | 仅 `game_id=_dFH…` 行 |
| Publishable Key（`sub=anon`） | **空** |
| service_role API Key | 全部 |

**结论 / 可行路径**：

1. **RLS + REST 隔离成立**（机制已验证）。
2. 「自定义登录 → `sub=game_{sid}`」**目前不能**直接用于 REST 数据面（网关不接受其 token，且缺 `role`）。
3. 可行方案（择一）：
   - **a（已验证）**：每游戏一个**网关身份**（用匿名登录创建，平台保存其 `sub` / `refresh_token`），`game_id` = 该 `sub`，RLS 按 `sub` 隔离；
   - **b（待验证）**：在控制台「身份认证→登录方式」启用自定义登录并**下载私钥**，确认其密钥是否注册到**网关侧**，使自定义 token 被 REST 接受；
   - **c（降级）**：游戏后端用 `service_role` API Key + 应用层强制 `game_id` 过滤（隔离弱化，不推荐）。

## 三、对规格的改动（**重要**）

现行规格这些条款**已被证伪，必须重写**：

- §5.3 映射表：`数据库 schema = game_{sid}`、`数据库 role = game_{sid}_rw`
- §6.4 `provision_database()`："开通独占数据库（schema + role），返回连接串"
- §6.5 `R-DB-1`（每游戏独立 schema+role）、`R-DB-2`（必须 PG 协议直连，不用 PostgREST）
- §9 "游戏数据库使用独占 schema + 专属 role，不使用 CloudBase 角色与 RLS"

**建议的新模型（二选一，待决策）**：

- **方案 A（贴合 CloudBase，推荐）**：单一 `public` schema；每游戏数据带 `game_id` 列；用 **RLS** 按 JWT claim/`sub` 或 `game_id` 隔离；游戏后端经 **PostgREST HTTP API / JS SDK** 访问；平台用 `ExecutePGSql` 建表与策略。**无需直连、无需建 role、彻底绕开沙盒网络问题。**
- **方案 B（保留直连）**：控制台创建**一个**服务登录账号，游戏服务经**内网/VPC**直连；隔离退化为「共享账号 + `game_id` 条件 + RLS」；平台侧仍需 `ExecutePGSql` 做 DDL。适用于需要事务/复杂 SQL/连接池的场景，但**不能**做每游戏独立 role。

> **决策（2026-10-02）：采用方案 A**（云 PG + PostgREST + JWT + RLS）。`docs/spec/技术架构规格.md` 已按此修订。

> 另：平台自身元数据（users/games/versions…）也建议落到同一 PG（`public` 或独立 schema），用 `ExecutePGSql` 建表；如需独立 schema，`CREATE SCHEMA` 可行。

## 四、复现

```bash
ENV=test-agent-d5ghby2pe53e38f28
# 沙盒内：PostgREST 可达
curl -s -H "Authorization: Bearer <Publishable Key>" \
  "https://$ENV.api.tcloudbasegateway.com/v1/rdb/rest/<table>?select=*"
# 沙盒内：直连 PG 不可达
timeout 8 bash -c 'cat < /dev/null > /dev/tcp/28.72.71.124/50733' && echo OPEN || echo UNREACHABLE
# 建 role 失败
tccli tcb ExecutePGSql --EnvId "$ENV" --Sql "CREATE ROLE x LOGIN PASSWORD 'p'" --region ap-shanghai
```
