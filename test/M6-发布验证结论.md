# M6 发布验证结论

- 日期：2026-10-02
- 范围：**M6-1 CloudRun 是否支持 WebSocket**、**M6-2 CloudRun → CloudBase PG**
- 结论：**两者均可行**。CloudRun（容器型）支持 WebSocket；访问数据库走**公网 PostgREST HTTP API** 即可，**无需 VPC**。

## 一、结论要点

1. **WebSocket：支持** ✅
   - 实测：部署 Socket.IO 服务到云托管，客户端 `wss` 连接 `transport=websocket`，收到 `hello` 并成功 `echo`。
   - **限制（官方）**：云托管请求超时 60s；**WS/SSE 建立后 60s 无数据则网关主动断开**。**须心跳**（建议每 10s）。可配的 10–7200s WS 超时是"HTTP 云函数"的能力，**不适用于容器型云托管**。
2. **CloudRun → 数据库：可行** ✅（走 PostgREST）
   - 云托管实例出公网即可访问 `https://<envId>.api.tcloudbasegateway.com/v1/rdb/rest/...`；
   - 实测：服务内 `/db` 用**环境变量注入**的 Publishable Key 调 PostgREST → **200** 返回数据。
   - 因此**不需要**给云托管配 VPC（也无需控制台 DB 账号）。若坚持 PG 协议直连，才需 VPC + 内网地址 + 控制台账号。
3. **单服务同源：可行** ✅
   - 同一服务同时提供 `HTTP API` 与 `WebSocket`（同源）；静态前端可同服务托管。
   - 环境变量注入、默认公网域名、端口配置均验证通过。

## 二、实测证据

| 验证 | 方式 | 结果 |
|---|---|---|
| 部署 | `manageCloudRun deploy`（源码构建，容器型，Port=3000） | 成功，版本 003，流量 100% |
| HTTP | `GET https://ws-probe-…sh.run.tcloudbase.com/` | 200 `{"ok":true,...}` |
| DB | `GET /db`（服务内 fetch PostgREST） | 200 `[{"id":1,...}]` |
| **WebSocket** | python-socketio `transports=["websocket"]` | connected, transport=**websocket**, hello/echoed OK |
| 环境变量 | 服务 `EnvParams` 注入 `PUBLISHABLE_KEY`/`DB_REST_URL` | `/db` 读到并生效 |
| 默认域名 | `detail` → `DefaultDomainName` | `https://ws-probe-322496-11-1327210567.sh.run.tcloudbase.com`（另有 `*.ap-shanghai.run.wxcloudrun.com`） |

## 三、关键坑

1. **源码构建偶发瞬时失败**：首次部署在推送镜像到 CCR 时报
   `Put "https://ccr.ccs.tencentyun.com/…: write tcp …: broken pipe` → **直接重试即成功**（第二次 normal）。
2. **端口必须与服务监听一致**（容器型默认要在"容器配置→端口"显式填写；本测试用 3000）。
3. **默认域名仅建议测试**；生产建议绑自定义域名（默认域名可能弹中间页）。
4. `MinNum=0` 可缩容到 0 省钱，但有冷启动；需要常驻可设 1。
5. WS 心跳必须做（60s 空闲断开）。

## 四、对规格的改动

- §6.7 / §7（发布）：确认「单服务同源 = 静态前端 + HTTP API + WebSocket」可行；补充 **WS 60s 空闲 + 10s 心跳**约束。
- 游戏服务访问数据库：**首选 PostgREST HTTP API（公网，无需 VPC）**；仅当需要事务/复杂 SQL 时再评估 VPC 直连（见 `test/M4-数据库验证结论.md`）。
